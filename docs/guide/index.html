A generalised, AI-legible, versioned governance framework — one portable payload of documentation standards, planning and execution protocols, adversarial TDD, contract-first execution loops, durable agent state, and governance inheritance that any AI agent or engineering team can consume, in any runtime, for any project. Nizam ships no application code, infrastructure, or runtime services.

Problem → Solution

Four named design decisions remediate four recurring flaws in agent-driven engineering pipelines. Each is binding on the framework's own implementation.

DD-1 — Tool-Driven State Management O(1) Lookup

Flaw remediated: context exhaustion from bulk-reading governance directories.

Agents route through the root NIZAM.json capability index (validated against registry/nizam-index.schema.json) to locate only the minimal governance files a task needs, instead of reading an entire standard/, methodology/, templates/, schema/, tools/, or ecosystem/ directory "just in case." Authoritative in methodology/04_tool_driven_state.md.

DD-2 — Universal Circuit Breaker Bounded Retries

Flaw remediated: infinite retry loops.

Execution stops after six failed executions per task or three failures with one signature, and configured step limits remain finite. Successes and decomposition or amendment labels do not erase failures. Only explicit finite task-scoped operator recovery can reopen a budget; invariant and authority breaches halt immediately. Authoritative in methodology/03_circuit_breaker.md.

DD-3 — Evidence Externalisation Tamper-Evident

Flaw remediated: brittle proof pasted inline into YAML or JSON strings.

Every piece of proof that a step succeeded is written to its own file under .agent/evidence/ and referenced by path, never pasted inline. See methodology/04_tool_driven_state.md Section 3.

DD-4 — Unified Skill Payload Runtime-Agnostic

Flaw remediated: duplicated, per-runtime skill forks.

Exactly one skill payload ships under tools/ — no .claude/, .codex/, or other per-runtime fork directories. Any runtime loads the same tools/SKILL.md through the adapter contract in tools/interface.md.

Quickstart

Governance inheritance is one atomic clone → inject → verify operation, implemented once as bootstrap.sh at the framework's repository root — an evolution of AGIP (the earlier prototype this framework evolved from, per bootstrap.sh's own header comment) into a single, reusable, runtime-agnostic script. From a checkout (or vendored copy) of the framework at a pinned tag, run:

GOVERNANCE_TAG=v2.0.0 ./bootstrap.sh --tag v2.0.0 --expected-sha '603afc7b17919334a6a01df1e39e63798d9d0acd' --git-repo .nizam-ref/

GOVERNANCE_TAG (or the equivalent --tag flag) is required and never defaulted: an empty tag, main, master, HEAD, or any refs/heads/* branch reference is refused, because a floating branch is never an acceptable inheritance pin (standard/GIP.md Section 2, point 1).

This clones the pinned tag, verifies --expected-sha before staging, stages the governance payload, verifies it landed correctly, retains the verified tag repository at .nizam-ref/ when --git-repo is supplied, and only then atomically installs the payload under the target directory (.nizam/ by default). What you get:

.nizam/
├── standard/
├── templates/
├── schema/
├── tools/
├── methodology/
├── ecosystem/
├── NIZAM.json
└── provenance.json

To check an already-bootstrapped target for drift, with no network access and no write, run:

GOVERNANCE_TAG=v2.0.0 ./bootstrap.sh --verify-only --tag v2.0.0 --expected-sha '603afc7b17919334a6a01df1e39e63798d9d0acd' --git-repo .nizam-ref/ --require-content-integrity

--verify-only performs no network clone, no write, and never executes code from inside .nizam/: with --git-repo .nizam-ref/ and --expected-sha, it verifies the complete file inventory, exact byte digests, and executable modes against the pinned commit tree (content_integrity=verified). For an unpacked release directory without a Git repository, --source-root DIR reports content_integrity=directory_match_unbound; --structural-only checks structure and provenance pins only (content_integrity=not_checked).

Adoption Paths

New repository

Per the Governance Inheritance Protocol (GIP) (standard/GIP.md Section 2): clone a pinned semantic-version git tag of the framework (never main or any floating branch), inject standard/, methodology/, templates/, schema/, tools/, and ecosystem/ together with the root NIZAM.json capability index into your workspace, load the injected documents into working context before acting, and record the pinned tag as your inheritance baseline. bootstrap.sh performs this as one atomic clone → inject → verify operation (Section 2.1).

Existing repository

A repository is rarely empty when it first adopts Nizam. standard/GIP.md Section 5 governs coexistence:

  • Conflict rules. A pre-existing CONTEXT.md, AGENTS.md, or CI (continuous integration) configuration is never silently overwritten. Bootstrap injects only standard/, methodology/, templates/, schema/, tools/, ecosystem/, and NIZAM.json; a colliding pre-existing file is preserved under a renamed path (for example CONTEXT.md.pre-nizam) so a human or agent can diff it against the framework's templates/ version and reconcile by hand. Existing CI is reconciled — the recommended compliance checks are added to it, not substituted for it.
  • Tier 1 — docs-standard-only. Inherit standard/ alone. Agents read and are bound by the governance documents; no Generator/Validator/Evaluator cycle runs yet.
  • Tier 2 — templates. Additionally inherit templates/, so the repository can author its own governed CONTEXT.md, AGENTS.md, ADRs, and other project documents, still without running the contract loop.
  • Tier 3 — full loop. Inherit the complete governance payload and run the complete contract-first Generator/Validator/Evaluator cycle described in methodology/01_execution.md, end to end.

Start paths

v2.0.0 migration: pin typed verification before begin and provide assessed structured per-check proof for completion. Read the consumer migration guide. The onboarding examples pin the published tag's exact commit; record consumer upgrade authorization before installation.

Three ways to begin work, using the same Planner, Generator, Validator, and Evaluator roles as the execution loop below. The feature path is that full loop. The bug-fix path and the small-change path are shorter routes over those roles, not a second process. The paths below name their artifacts and the point at which implementation may begin. Opening methodology/ is not required to choose one.

The feature path covers Spec Kit's specify-before-build sequence and Superpowers' design-then-plan entry. The bug-fix path covers Spec Kit's assessed cause, scoped fix, and recorded verification. The small-change path covers BMAD Method's right-sized process and Superpowers' quick task. These sentences name documented properties. They do not rank this framework against those projects. A comparison sentence belongs only beside a recorded run of the preregistered study in docs/planning/agentic-excellence.md. That study has not been executed.

New feature

Specify what to build and agree the design before planning the implementation.

  • .agent/product_spec.md and .agent/feature_list.json — the specification.
  • .agent/contracts/NNN.json — scope, non-goals, and verification commands, starting at status: "proposed".
  • An independent pre-code verdict under .agent/validator/ and a contract-review verdict under .agent/qa/.
  • After implementation, an independent post-implementation check under .agent/validator/ and a recorded verification result under .agent/qa/, with command output under .agent/evidence/.

Implementation may begin only after the contract is approved. The feature is not done until that independent post-implementation check and that recorded verification result both exist. The loop below is this path. Each verdict counts only when approved is true and issues, missing_acceptance_coverage, and unsupported_claims are empty.

Bug fix

Record an assessed cause, a scoped fix, and a recorded verification result.

  • .agent/evidence/<id>-cause.json — the assessed cause.
  • .agent/evidence/<id>-scope.json — the scoped fix: the files in scope and the non-goals.
  • .agent/qa/<id>.json — the recorded verification result, with command output under .agent/evidence/.

Implementation may begin once the assessed cause and the scoped fix are both recorded. tools/start_path.py begin bugfix --id <id> is that decision: it exits 0 only when those two records validate. The bug fix is not done until the recorded verification result exists, which tools/start_path.py done bugfix --id <id> checks. A repair that stays inside an already approved contract does not open a new feature specification or repeat the feature path's pre-code contract gates.

Small unambiguous change

Record the intent, make the change, and record a verification result.

  • .agent/evidence/<id>-intent.json — the intent.
  • .agent/qa/<id>.json — the recorded verification result, with command output under .agent/evidence/.

Implementation may begin once the intent is recorded. tools/start_path.py begin small-change --id <id> is that decision, and tools/start_path.py done small-change --id <id> checks the recorded verification result. The small-change path records intent and a verification result and does not require the full feature-gate stack. Use the feature path when the change needs a new contract.

Semantic task routing and execution helpers

Before starting work, run tools/start_path.py classify to classify the change into trivial, bugfix, small-change, standard-feature, or high-risk based on canonical relative paths and semantic change properties, along with work-specific diagnostic stopping rules. The CLI also provides tools/start_path.py begin trivial --id <id> and tools/start_path.py done trivial --id <id> for bounded doc/comment/test-only edits, amend-contract for mechanical scope or command updates to an approved contract, preflight for host capability discovery, capture for exclusive non-overwriting evidence capture with continuation-lineage tracking, publish (defaulting to noncommitting --mode prepare, with --mode publish externally mediated via NIZAM_MUTATION_ADAPTER and --mode finalize verifying committed stage deltas), build-receipt, status, and resume.

The Execution Loop

Under the Agent Governance Framework (AGF) (standard/AGF.md), every feature moves through a two-loop, contract-first state machine (methodology/01_execution.md) before it is considered complete:

  1. Planner expands a request into a specification and feature list.
  2. Generator proposes a contract (status: "proposed") scoping the feature's deliverables, non-goals, and verification commands.
  3. Validator Mode A — the pre-code contract gate — confirms the contract is complete, bounded, testable, and traceable to the specification.
  4. Evaluator contract review — an independent second read of the same contract.
  5. Generator implements only the approved contract's scope.
  6. Validator Mode B — the post-code implementation gate — diffs the resulting change set against the approved contract, confirming only contracted files were touched and nothing is a stub.
  7. Evaluator QA verdict — independently executes the contract's verification commands and records a pass/fail verdict with evidence.

Validator Mode A, Validator Mode B, the Evaluator's contract review, and the Evaluator's QA verdict each culminate in a machine-parseable JSON verdict; advancement is permitted only when approved is true and issues, missing_acceptance_coverage, and unsupported_claims are all empty (standard/AGF.md Section 4).

Every repeatable step above — a contract revision after a Mode A or contract-review rejection, or an implementation rework after a Mode B or QA rejection — is governed by the framework's work-specific diagnostic stopping and circuit-breaker policy (methodology/03_circuit_breaker.md): attempt 1 is a direct fix, attempt 2 a type/interface analysis, and attempt 3 an architectural review; reaching the attempt threshold triggers work-specific diagnosis or bounded decomposition when invariants hold, whereas invariant breaches, specification contradictions, or repeated unresolved defect signatures mark the step BLOCKED, log the failure to the technical-debt register, and escalate for human review.

Anatomy of a Governed Repository

A repository governed by Nizam communicates results exclusively through durable, file-based state — never through chat history or conversational memory (the durable-state rule, standard/AGF.md Section 5). Every run maintains its position through file families under .agent/:

.agent/
├── run_state.json      # current phase/feature position, status, circuit-breaker counters, history
├── feature_list.json   # the planned feature DAG: dependencies and acceptance tests
├── contracts/
│   └── NNN.json        # per-feature scope: deliverables, non-goals, verification commands
├── qa/
│   └── NNN.json        # the Evaluator's independent pass/fail verdict, with evidence
└── evidence/
    └── *.txt           # captured terminal output, one file per verification command

Lifecycle: a Planner writes feature_list.json; a Generator writes a proposed contracts/NNN.json; once both Validator gates approve, the Generator implements and captures proof to evidence/; the Evaluator writes the corresponding qa/NNN.json verdict; run_state.json then advances to the next eligible feature. See methodology/04_tool_driven_state.md Section 4.

Agent Integration & llms.txt

Machine-Legible LLM Endpoints: External AI agents, IDE copilots, and documentation indexers can ingest llms.txt (concise operational index) or llms-full.txt (complete single-file CLI, role, permission-class, and schema reference) directly from the repository root or GitHub Pages site root.

An agent runtime discovers the skill payload per tools/interface.md Section 2, in this order:

  1. Bootstrapped-consumer discovery. First look for tools/skill.json under the injected governance target directory — by default .nizam/tools/skill.json.
  2. Framework-checkout fallback. If no .nizam/tools/skill.json is found, fall back to a repository-root tools/skill.json — the layout this framework repository ships at its own root for a framework checkout evaluating itself.
  3. Pinned-checkout discovery. Where a consumer instead references a pinned release tag without vendoring files locally, resolve tools/skill.json inside a checkout of that pinned tag.

Once tools/skill.json is located, every protocol this skill summarizes assumes an agent runtime can perform three core abstract operations (tools/interface.md Section 4), each mapped by the runtime's own adapter onto its native tool-calling primitives:

read-state
Read the current durable-state content a task needs — NIZAM.json, a governance module file, or a .agent/ artifact.
write-evidence
Persist a material result — a document, a durable-state update, or captured verification output — to its canonical durable location.
run-verification
Execute a contract's verification commands and capture the command's output and exit code as evidence.

For repository Git mutations during evidence publication (tools/interface.md Section 4.4), tools/start_path.py publish defaults to noncommitting --mode prepare (emitting a .publish-request.json envelope so the host runtime can commit Stage 1 and Stage 2 on top of intended_base and verify them with --mode finalize). When publish --mode publish or build-receipt --commit is invoked directly, it requires an explicit NIZAM_MUTATION_ADAPTER from the host runtime and never falls back to local git add or git commit.

An integrator adapting a new runtime checks conformance against tools/interface.md Section 5's numbered checklist, condensed here: the adapter locates tools/skill.json, loads its entry_point (tools/SKILL.md) content verbatim rather than a paraphrase, injects it as instructions-tier context rather than ordinary conversation, loads it conditionally on the triggers tools/SKILL.md Section 1 defines, maintains no forked or rewritten copy of it, backs all three abstract operations above with a real file-read, file-write, and command-execution primitive respectively, surfaces every operation's errors rather than suppressing them, and does not fabricate governance behavior when no tools/skill.json can be discovered.

FAQ

What is Nizam not?
Nizam is a pure governance / methodology payload. It ships standards, protocols, schemas, and templates — it does not ship application code, infrastructure, or runtime services.
How is a version pinned?
Consumers clone a specific semantic-version git tag (for example v2.0.0) and verify its expected commit digest (--expected-sha), never main or any other floating branch reference (standard/GIP.md Section 2, point 1).
How is drift detected, and how is it fixed?
A consumer periodically re-verifies its injected governance content against its retained pinned tag repository (./bootstrap.sh --verify-only --tag v2.0.0 --expected-sha '603afc7b17919334a6a01df1e39e63798d9d0acd' --git-repo .nizam-ref/ --require-content-integrity), checking for local hand-mutation and staleness against newer releases (standard/GIP.md Section 4). The correct remediation is always to re-run bootstrap.sh against the appropriate tag — hand-patching an individual injected file is prohibited, because it reintroduces exactly the divergence drift detection exists to catch.
